# BlackRouter Goals and Implementation Roadmap

> **Status snapshot: 2026-10-27.** This roadmap records the current scope decisions and the latest reviewed PR #2 validation notes available on this date. CI results and provider terms are time-bound; recheck the linked branch/workflows and official provider documentation before implementation or release.

## 1. Product Definition

BlackRouter is **Tiny 9Router for OpenChamber**: a lightweight local gateway integrated into OpenChamber, not a standalone replacement for the complete 9router application.

The target experience is to route requests from OpenChamber/OpenCode and compatible clients through useful free AI providers—including providers that do not require the user to supply an API key—while providing reliable request translation, model routing, token saving, and optional proxy/relay pools.

- Main repository: [Yoganataa/blackrouter](https://github.com/Yoganataa/blackrouter)
- Primary behavior and feature reference: [decolua/9router](https://github.com/decolua/9router)
- Lightweight implementation reference: [luqman-v1/9router-go](https://github.com/luqman-v1/9router-go)
- Additional comparative reference: [cheaper-inference/OmniRoute](https://github.com/cheaper-inference/OmniRoute)

## 2. Architecture Rules

1. **Use official 9router as the backend behavior reference.** Port/adapt its useful core behavior and fixes into BlackRouter's current architecture; do not copy the full application.
2. **Use 9router-go selectively.** Borrow small, relevant implementation patterns where they simplify or improve the gateway. Do not port its entire Go service or embedded Svelte dashboard.
3. **Keep OpenChamber as the host UI.** Reproduce 9router's useful information architecture and interaction patterns only to the extent that the OpenChamber panel SDK, sandbox, theme, lifecycle, and available space allow.
4. **Preserve BlackRouter-specific boundaries.** Provider execution/request translation belongs in the core; OpenChamber host integration, local transport, configured HTTP proxy/relay handling, and response-stream adaptation remain explicit integration layers.
5. **Adopt features by value, not parity count.** Every feature must be useful, compatible with the extension model, testable, maintainable, and compliant with source licenses.
6. **Do not equate a checked-in bundle with a verified build.** Generated runtime bundles must be regenerated by the project's build process and checked against source.
7. **Keep behavior honest.** Do not claim provider availability, successful tests, token savings, or feature parity without evidence.

### Locked functional requirements

#### MUST — first stable baseline

- **FR-M1 — OpenChamber integration and local gateway.** BlackRouter runs as a native OpenChamber extension and exposes its local OpenAI-compatible gateway on loopback by default (`127.0.0.1:20128/v1`).
- **FR-M2 — Compatible request interface.** Serve the model catalog and Chat Completions with streaming SSE and non-streaming JSON. Route model-specific OpenCode Free requests through the appropriate Chat Completions, Responses, or Messages translator where required.
- **FR-M3 — Default no-user-API-key path.** OpenCode Zen Free remains the default upstream; a user-supplied API key is not mandatory for this default lane. An optional custom OpenAI-compatible upstream and its credential remain supported.
- **FR-M4 — Native OpenCode behavior.** Preserve the required provider headers, request/tool fingerprints, session affinity, model-specific translation, and catalog behavior. Test Model must send a real short inference request rather than report success based only on connectivity.
- **FR-M5 — Explicit transport policy.** Support the configured direct, HTTP forward-proxy, and relay paths. A request routed through a selected proxy/relay must not silently escape through direct egress. Try only eligible configured alternatives; if none is safe, return the actionable upstream failure.
- **FR-M6 — Failure-safe request lifecycle.** Handle streaming, first-byte keepalive where applicable, client cancellation/disconnect, timeouts, upstream errors and status/body propagation. Retries and fallback must be bounded and must not loop.
- **FR-M7 — Security and secret handling.** Bind to loopback unless explicitly configured otherwise; redact credentials from logs, diagnostics and panel state; do not commit tokens or keys.
- **FR-M8 — Reproducible quality gate.** Pass type-check and automated tests, build all shipped bundles from source, inspect generated diffs, and perform relevant OpenChamber host plus direct/proxy/relay smoke tests before calling the baseline complete.

#### SHOULD — implement only after MUST is stable

- **FR-S1 — Proxy-pool reliability and operation.** Validate pool selection strategies, health/test status, cooldown/recovery, safe alternate-pool handling, and the corresponding native-panel controls.
- **FR-S2 — Linear token-saver combo.** Integrate the relevant 9router-go token-saving behavior, RTK tool-output compression, Caveman concise-output transformation, and I Have ADHD scannable-response transformation as one documented, ordered pipeline. Preserve errors, exit codes, paths, line numbers, useful diffs, structured/tool arguments and context needed for the next tool call. The stage order is fixed as: (1) 9router-go token-saver behavior, (2) RTK, (3) Caveman, (4) I Have ADHD. Treat this as one combo with a single top-level enable/disable control; do not expose four unrelated profiles as the primary UX. Each stage must have an explicit input/output contract and regression coverage, and must not corrupt code literals, secrets, tool calls or safety-critical context. Measure token savings with repeatable representative tasks.
- **FR-S3 — Provider adapter boundary.** Introduce a maintainable provider registry/adapter contract before adding provider-specific branches throughout the gateway. Add providers incrementally, with request/response translation, capabilities, auth requirements, rate-limit behavior and tests.
- **FR-S4 — Approved provider integrations.** After FR-S3 and after all FR-M1–FR-M8 exit criteria pass, assess and implement CodeBuddy CN, WorkBuddy/Tencent TokenHub, and Freebuff individually under the provider gates above. Use documented authentication and endpoints, distinguish OAuth/account-bound, API-key, limited-free, trial/credit and paid access, and block any integration whose terms, privacy, credential handling or API stability cannot be validated. Do not make a user-supplied API key mandatory for the default OpenCode Zen Free lane.
- **FR-S5 — Bounded model combos and fallback.** Preserve named model aliases/combos and fallback chains only with explicit limits, cycle protection and useful error reporting.
- **FR-S6 — Core panel workflows.** Provide clear model/router/proxy-pool configuration and actionable loading, empty, success and failure states within OpenChamber's native extension constraints.

These ideas are intentionally separated from the locked functional requirements. Do not implement them until a future scope-change request promotes them:

- **WL-C1 — Standalone Caveman profile outside the linear combo.** Not included unless a future scope change explicitly requests a separately configurable profile.
- **WL-C2 — Standalone I Have ADHD profile outside the linear combo.** Not included unless a future scope change explicitly requests a separately configurable profile. Inside FR-S2, these stages are part of the one linear combo and must not be treated as interchangeable.

### WON'T — excluded from this scope

- Porting the entire official 9router application or the entire 9router-go service/dashboard.
- Replacing OpenChamber's native panel with a separate standalone dashboard.
- Porting the closed/unmerged 9router PR #5235 Bun-sidecar design without new evidence and a separately approved design decision.
- Automatically bypassing a selected proxy/relay by switching to direct egress without explicit policy.
- Claiming providers are unlimited/permanently free or advertising token-savings percentages without current evidence.
- Adding providers beyond the three approved targets without a scope change, or shipping any target before its documentation, terms, auth/security and runtime acceptance gates pass.
- Harvesting desktop cookies/session credentials or adopting undocumented/private provider endpoints as a workaround for missing supported access.

### Change-control rule

This is a scope freeze, not a prohibition on defect fixes. The three named provider targets are the only feature expansion explicitly approved in `BR-SCOPE-1.1`; their implementation remains gated behind the Must baseline and the provider-specific acceptance criteria above. Any other feature addition, promotion from COULD/WON'T, or removal of a MUST requires a separate scope-change proposal stating the user problem, MoSCoW change, implementation/test impact, security and compatibility risks, and why it cannot fit the current baseline. ## 3. Current Repository Baseline

The default branch currently contains a TypeScript/Bun OpenChamber extension with:

- An OpenAI-compatible local service configured by default at `127.0.0.1:20128/v1`, including `/v1/models` and `/v1/chat/completions` with streaming and non-streaming responses.
- OpenCode Zen Free as the default upstream, with configurable OpenAI-compatible upstream URL and optional locally stored/redacted Bearer key.
- OpenCode-specific request headers, tool fingerprints, session affinity, and model-based routing for Chat Completions, Responses, and Messages endpoints.
- Proxy/relay pools for HTTP forward proxy, Cloudflare Workers, Vercel Edge, Deno Deploy, and Netlify Functions, with selectable routing strategies and pool test/status data.
- RTK token-output compression, optional Caveman and Ponytail prompt profiles, named model combos/fallback, dynamic model metadata, OpenCode provider registration, and a native OpenChamber panel with model/router/proxy-pool views.

These are baseline features documented or present in the repository—not proof that every path has passed current CI or live provider testing. The current provider core is primarily the OpenCode Free path; BlackRouter is not yet a complete multi-provider port of 9router.

### Phase 3 — Linear Token-Saver Combo (FR-S2, SHOULD)

The four components are one sequential combo, not four unrelated features or four primary UI toggles. Pipeline order is fixed: **9router-go token-saver behavior → RTK → Caveman → I Have ADHD**. The combo has one top-level enable/disable control. Internally, each stage must retain a clear contract and test boundary so failures can be isolated without changing the defined order.

#### 3.1 Establish source behavior and provenance

- [ ] Inspect the current 9router-go implementation and identify the specific token-saving behavior to adapt; do not port its entire Go service or dashboard.
- [ ] Pin upstream revisions, paths, licenses and local modifications for 9router-go, RTK, Caveman and I Have ADHD behavior.
- [ ] Research exact current official 9router behavior for Caveman and exact I Have ADHD semantics; do not equate I Have ADHD with Ponytail or Caveman.
- [ ] Define the stage input/output contract and failure behavior before composing the pipeline.

#### 3.2 Implement the linear stages in order

- [ ] Stage 1 — adapt only the relevant 9router-go token-saver behavior.
- [ ] Stage 2 — apply RTK tool-output compression, preserving errors, exit status, paths, line numbers, meaningful diffs and downstream-useful context.
- [ ] Stage 3 — apply Caveman concise-output transformation without removing required steps, constraints, code, diagnostics or safety-relevant information.
- [ ] Stage 4 — apply I Have ADHD scannable-response transformation, preserving technical completeness and context.
- [ ] Keep the order deterministic; define whether a stage can no-op safely and how errors are surfaced. Do not silently skip a failed stage if doing so could corrupt or lose required context.
- [ ] Expose one top-level combo toggle and document the fixed stage order; do not make independent stage toggles the primary configuration model.

#### 3.3 Regression and measurement

- [ ] Add per-stage and end-to-end regression tests for coding, debugging, long outputs, tool calls, and multi-step workflows.
- [ ] Preserve code literals, structured arguments, file paths, tool identifiers, secrets, error messages, exit codes, diffs and safety-critical context.
- [ ] Compare output quality and token counts against the unmodified baseline on repeatable representative tasks.
- [ ] Report measured results and methodology; do not claim universal savings percentages.

**Exit criteria:** all four stages run in the specified linear order behind one combo control; provenance is recorded; stage and end-to-end tests pass; repeatable measurements show the actual impact without unacceptable loss of context or correctness.

### Phase 4 — Proxy Pools and Egress Reliability

Proxy/relay pool functionality already exists in the repository. This phase is to validate and harden it, not to rebuild it from scratch.

- [ ] Verify HTTP forward-proxy and Cloudflare, Vercel, Deno, and Netlify relay implementations.
- [ ] Verify pool selection strategies, pool health/test status, cooldowns, and recovery behavior against the current code.
- [ ] Ensure a rate-limited or provider-rejected pool is not retried indefinitely.
- [ ] On a provider-specific rejection, try only explicitly configured eligible alternate routes and keep the failed pool excluded for the remainder of the request where appropriate.
- [ ] Do not silently switch to direct egress when a configured proxy was selected for privacy or policy reasons.
- [ ] Preserve original status/body if no safe eligible fallback exists.
- [ ] Test unavailable relays, invalid proxy configuration, all pools unhealthy, cooldown expiry, client cancellation, and recovery.
- [ ] Keep proxy credentials and relay deployment tokens out of logs, UI state, and committed files.

**Exit criteria:** proxy pools route predictably, fail safely, and expose diagnosable status without violating the configured egress policy.

### Phase 5 — OpenChamber Panel and 9router UX Parity

The panel already has model, router, OpenCode, and proxy-pool views, and the open PR includes a panel redesign. Build on those components rather than introducing a second dashboard.

- [ ] Validate the current panel redesign inside OpenChamber, not only by inspecting bundle syntax.
- [ ] Use 9router as an interaction/information-architecture reference, not as a requirement to copy its standalone Svelte dashboard.
- [ ] Prioritize provider/model browsing, route/combo configuration, token saver controls, proxy pools, Test Model, and actionable diagnostics.
- [ ] Keep OpenChamber theme tokens, keyboard navigation/focus, reduced-motion behavior, and narrow-panel responsiveness.
- [ ] Provide accurate loading, empty, success, warning, and failure states.
- [ ] Keep sensitive credentials masked and avoid duplicate host-level settings.
- [ ] Regenerate the panel bundle from source and verify reload/persistence behavior.

**Exit criteria:** the panel is visually coherent with the useful 9router workflows while remaining a stable native OpenChamber extension.

### Phase 6 — Release Hardening

- [ ] Pass type-check, unit tests, build, and relevant CI checks.
- [ ] Test core flows in the actual supported OpenChamber version.
- [ ] Test direct/proxy/relay transport, all supported endpoint formats, streaming, cancellation, rate limits, and fallback.
- [ ] Audit local service binding, API-key handling, relay deployment secrets, logs, and settings persistence.

**Exit criteria:** clean reproducible build, passing required checks, verified primary workflows, and accurate documentation.

## 7. Engineering Rules

- Make one coherent change at a time and keep PRs reviewable.
- Read repository instructions and inspect relevant code/tests before editing.
- Check official 9router PRs and commits at implementation time; do not rely only on old PR descriptions.
- Keep upstream adaptations narrow and documented.
- Add regression tests for every behavior fix.
- Do not commit secrets or expose credentials in errors, logs, panel state, or diagnostics.
- Bind the local gateway to loopback by default unless the user explicitly configures and protects broader exposure.
- Use bounded retries, timeouts, concurrency, and buffering.
- Treat upstream responses and model catalogs as untrusted input.
- Keep user prompts and model output out of telemetry by default.
- Do not mark a checklist item complete until the implementation is present and validation evidence exists.

## 8. Definition of Done

A change is complete only when:
- [ ] It solves a defined user problem and fits BlackRouter's architecture.
- [ ] Tests cover normal behavior and important failure modes.
- [ ] Type-check/build and relevant CI checks pass.
- [ ] Generated bundles are reproducible from source.
- [ ] Existing API compatibility and configured egress behavior remain intact.
- [ ] Errors are actionable and secrets are redacted.
- [ ] Documentation reflects verified behavior.
- [ ] Upstream provenance and license requirements are satisfied where relevant.

## 9. Explicit Non-Goals

- Porting all of official 9router into BlackRouter.
- Porting the entire 9router-go application or its dashboard.
- Replacing the OpenChamber panel with a standalone web application.
- Adding a large number of providers before the core/provider adapter boundary is validated.
- Porting the closed Bun-sidecar PR #5235 without new evidence that it is required.
- Claiming tests, provider availability, unlimited free usage, or token-savings percentages without verification.
