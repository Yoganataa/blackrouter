# BlackRouter Goals and Implementation Roadmap

> **Status snapshot: 2026-10-26.** This roadmap reflects the repository's current `main` branch, the open implementation PR, and the upstream references reviewed on this date. Re-check GitHub before treating any status below as current.

## 1. Product Definition

BlackRouter is **Tiny 9Router for OpenChamber**: a lightweight local gateway integrated into OpenChamber, not a standalone replacement for the complete 9router application.

The target experience is to route requests from OpenChamber/OpenCode and compatible clients through useful free AI providers—including providers that do not require the user to supply an API key—while providing reliable request translation, model routing, token saving, and optional proxy/relay pools.

- Main repository: [Yoganataa/blackrouter](https://github.com/Yoganataa/blackrouter)
- Primary behavior and feature reference: [decolua/9router](https://github.com/decolua/9router)
- Lightweight implementation reference: [luqman-v1/9router-go](https://github.com/luqman-v1/9router-go)

## 2. Architecture Rules

1. **Use official 9router as the backend behavior reference.** Port/adapt its useful core behavior and fixes into BlackRouter's current architecture; do not copy the full application.
2. **Use 9router-go selectively.** Borrow small, relevant implementation patterns where they simplify or improve the gateway. Do not port its entire Go service or embedded Svelte dashboard.
3. **Keep OpenChamber as the host UI.** Reproduce 9router's useful information architecture and interaction patterns only to the extent that the OpenChamber panel SDK, sandbox, theme, lifecycle, and available space allow.
4. **Preserve BlackRouter-specific boundaries.** Provider execution/request translation belongs in the core; OpenChamber host integration, local transport, configured HTTP proxy/relay handling, and response-stream adaptation remain explicit integration layers.
5. **Adopt features by value, not parity count.** Every feature must be useful, compatible with the extension model, testable, maintainable, and compliant with source licenses.
6. **Do not equate a checked-in bundle with a verified build.** Generated runtime bundles must be regenerated by the project's build process and checked against source.
7. **Keep behavior honest.** Do not claim provider availability, successful tests, token savings, or feature parity without evidence.

## 3. Current Repository Baseline

The default branch currently contains a TypeScript/Bun OpenChamber extension with:

- An OpenAI-compatible local service configured by default at `127.0.0.1:20128/v1`, including `/v1/models` and `/v1/chat/completions` with streaming and non-streaming responses.
- OpenCode Zen Free as the default upstream, with configurable OpenAI-compatible upstream URL and optional locally stored/redacted Bearer key.
- OpenCode-specific request headers, tool fingerprints, session affinity, and model-based routing for Chat Completions, Responses, and Messages endpoints.
- Proxy/relay pools for HTTP forward proxy, Cloudflare Workers, Vercel Edge, Deno Deploy, and Netlify Functions, with selectable routing strategies and pool test/status data.
- RTK token-output compression, optional Caveman and Ponytail prompt profiles, named model combos/fallback, dynamic model metadata, OpenCode provider registration, and a native OpenChamber panel with model/router/proxy-pool views.

These are baseline features documented or present in the repository—not proof that every path has passed current CI or live provider testing. The current provider core is primarily the OpenCode Free path; BlackRouter is not yet a complete multi-provider port of 9router.

## 5. Upstream PR Reference Policy

Check official 9router's current code and PR status before porting a fix. A PR's description is evidence of proposed behavior, not proof that it was merged or remains the preferred implementation.

Relevant references reviewed for this roadmap:

- [9router PR #5222](https://github.com/decolua/9router/pull/5222): OpenCode Free-tier session timestamp and CLI fingerprint fixes. BlackRouter's open PR describes adapting the relevant executor behavior. Recheck the latest upstream revision before syncing again.
- [9router PR #5235](https://github.com/decolua/9router/pull/5235): closed and unmerged Bun sidecar approach. Do **not** port that sidecar just because it appears in the PR. The current BlackRouter approach described in PR #2 uses the in-process transport and preserves proxy/relay boundaries. Re-evaluate only if upstream's current implementation or reproducible tests establish a need.
- [9router PR #5167](https://github.com/decolua/9router/pull/5167): SSE keepalive before the first response byte. Retain only if the BlackRouter transport and regression tests demonstrate the same need.
- [9router PR #4988](https://github.com/decolua/9router/pull/4988): OpenCode Free-tier 403 handling for proxied requests. Its described upstream proposal retries direct egress; BlackRouter's PR instead describes trying another configured proxy pool and not silently bypassing the selected egress policy. Preserve this privacy-aware behavior unless a deliberate product/security decision changes it.
- [9router PR #5193](https://github.com/decolua/9router/pull/5193): dashboard test behavior for the free lane. BlackRouter's PR describes retaining a real short inference request for Test Model and correcting the catalog User-Agent. Verify this against current upstream behavior and live tests before changing it.

When adapting any upstream code, record the upstream commit, source paths, license, and local modifications. Keep provenance notes alongside the copied/adapted code.

## 6. Phased Roadmap

Phases are ordered. Each phase should pass its exit criteria before unrelated feature work expands the scope.

### Phase 0 — Audit and Establish a Reproducible Baseline

- [ ] Map the current service, core/executor, request translators, response-stream adapter, panel, status view, proxy/relay transports, provider settings, and tests.
- [ ] Establish which capabilities exist on `main` and which are only on the open PR branch.
- [ ] Record the OpenChamber extension contract and supported endpoint/request formats.
- [ ] Build a feature-gap matrix against official 9router and 9router-go: feature, current BlackRouter status, source reference, user value, compatibility, risk, tests, priority.
- [ ] Capture current type-check, test, and build results before further refactoring.
- [ ] Verify license and provenance for adapted upstream code.

**Exit criteria:** current-main and PR-only changes are distinguished, and there is a reproducible validation baseline.

### Phase 1 — Core Gateway and Native OpenCode Path

**Current focus: unblock and validate PR #2.**

- [ ] Make type-check pass on the PR branch.
- [ ] Pass unit tests and build using the repository's Bun scripts.
- [ ] Regenerate and inspect shipped bundles from source.
- [ ] Verify gateway lifecycle/configuration and the OpenAI-compatible API contract.
- [ ] Verify native request translation and model-based Chat/Responses/Messages endpoint selection.
- [ ] Verify session/tool fingerprint stability and correct provider headers.
- [ ] Verify streaming, first-byte keepalive, cancellation, timeouts, upstream errors, and client disconnect behavior.
- [ ] Verify direct, HTTP proxy, and relay pool paths do not silently bypass configured egress policy.
- [ ] Verify Test Model behavior and dynamic model catalog behavior against the current official provider requirements.
- [ ] Ensure retry/fallback is bounded, does not create loops, and preserves the original actionable error when no safe fallback exists.
- [ ] Merge only after required checks and host-level verification pass.

**Exit criteria:** PR #2 is validated and integrated, core request paths work in OpenChamber, and generated bundles match source.

### Phase 2 — Provider Adapter Architecture and Free Provider Coverage

- [ ] Keep OpenCode Free as the initial supported no-user-API-key path until core reliability is proven.
- [ ] Design a provider adapter/registry boundary before adding more providers; do not scatter provider-specific conditions through the gateway.
- [ ] Identify providers that are genuinely free or do not require a user-supplied API key, using current official documentation and live verification.
- [ ] Distinguish no-key access from OAuth/account-bound access, API-key providers, trial credits, and paid services.
- [ ] Add providers one at a time with model metadata, auth requirements, request/response translation, capability handling, rate-limit behavior, and tests.
- [ ] Keep optional custom OpenAI-compatible upstreams supported without making credentials mandatory for the default path.
- [ ] Never advertise a provider as unlimited or permanently free without explicit, current evidence.

**Exit criteria:** each enabled provider has a tested adapter and clear authentication/usage requirements; adding a provider does not destabilize existing providers.

### Phase 3 — Token Saver

The current project already documents RTK and Caveman/Ponytail. The requested product target is **RTK, Caveman, and I Have ADHD**. Do not assume Ponytail and I Have ADHD are equivalent; inspect official 9router's current definitions and behavior first.

#### 3.1 RTK — tool-output compression

- [ ] Validate the existing RTK port against the pinned official source and regression tests.
- [ ] Test the filters used for git status/diff/log, search, file listing, numbered reads, build output, repeated logs, and large command output.
- [ ] Preserve errors, exit status, paths, line numbers, meaningful diffs, and details needed by subsequent tool calls.
- [ ] Preserve compatibility exports and existing call signatures used by BlackRouter.
- [ ] Measure token savings on representative coding tasks rather than claiming a universal percentage.
- [ ] Make RTK independently configurable and inspectable for debugging.

#### 3.2 Caveman — concise output profile

- [ ] Verify the exact official 9router behavior and prompt placement.
- [ ] Keep it independent from RTK, configurable, and off by default until validated.
- [ ] Reduce unnecessary prose without removing required steps, constraints, code, diagnostics, or safety-relevant information.
- [ ] Test coding, debugging, explanation, and multi-step tasks.

#### 3.3 I Have ADHD — scannable response profile

- [ ] Research the exact current upstream implementation and intended behavior before designing this profile.
- [ ] Implement as a separate toggle/profile, not as a rename of Ponytail or Caveman.
- [ ] Prefer concise, clearly prioritized, scannable instructions while preserving technical completeness and context.
- [ ] Add tests/examples for technical tasks and long multi-step workflows.

#### Shared acceptance criteria

- [ ] Profiles can be toggled independently.
- [ ] Processing order and interactions are documented.
- [ ] Code literals, file paths, tool identifiers, structured arguments, secrets, and safety-critical context are not corrupted.
- [ ] Before/after regression tests exist.
- [ ] Claims about savings are supported by repeatable measurements.

**Exit criteria:** all three requested features have defined, tested behavior, and each can be disabled independently.

### Phase 4 — Proxy Pools and Egress Reliability

Proxy/relay pool functionality already exists in the repository. This phase is to validate and harden it, not to rebuild it from scratch.

- [ ] Verify HTTP forward-proxy and Cloudflare, Vercel, Deno, and Netlify relay implementations.
- [ ] Verify pool selection strategies, pool health/test status, cooldowns, and recovery behavior against the current code.
- [ ] Ensure a rate-limited or provider-rejected pool is not retried indefinitely.
- [ ] On a provider-specific rejection, try only explicitly configured eligible alternate routes and keep the failed pool excluded for the remainder of the request where appropriate.
- [ ] Do not silently switch to direct egress when a configured proxy was selected for privacy or policy reasons.
- [ ] Preserve original status/body if no safe eligible fallback exists.
- [ ] Test unavailable relays, invalid proxy configuration, all pools unhealthy, cooldown expiry, client cancellation, and recovery.
- [ ] Keep proxy credentials and relay deployment tokens out of logs, UI state, and committed files.

**Exit criteria:** proxy pools route predictably, fail safely, and expose diagnosable status without violating the configured egress policy.

### Phase 5 — OpenChamber Panel and 9router UX Parity

The panel already has model, router, OpenCode, and proxy-pool views, and the open PR includes a panel redesign. Build on those components rather than introducing a second dashboard.

- [ ] Validate the current panel redesign inside OpenChamber, not only by inspecting bundle syntax.
- [ ] Use 9router as an interaction/information-architecture reference, not as a requirement to copy its standalone Svelte dashboard.
- [ ] Prioritize provider/model browsing, route/combo configuration, token saver controls, proxy pools, Test Model, and actionable diagnostics.
- [ ] Keep OpenChamber theme tokens, keyboard navigation/focus, reduced-motion behavior, and narrow-panel responsiveness.
- [ ] Provide accurate loading, empty, success, warning, and failure states.
- [ ] Keep sensitive credentials masked and avoid duplicate host-level settings.
- [ ] Regenerate the panel bundle from source and verify reload/persistence behavior.

**Exit criteria:** the panel is visually coherent with the useful 9router workflows while remaining a stable native OpenChamber extension.

### Phase 6 — Release Hardening

- [ ] Pass type-check, unit tests, build, and relevant CI checks.
- [ ] Test core flows in the actual supported OpenChamber version.
- [ ] Test direct/proxy/relay transport, all supported endpoint formats, streaming, cancellation, rate limits, and fallback.
- [ ] Audit local service binding, API-key handling, relay deployment secrets, logs, and settings persistence.
- [ ] Update README and changelog to reflect only verified functionality.
- [ ] Document known provider limitations and recovery steps.
- [ ] Do not release with unexplained CI failures or bundles that have not been reproduced by the build.

**Exit criteria:** clean reproducible build, passing required checks, verified primary workflows, and accurate documentation.

## 7. Engineering Rules

- Make one coherent change at a time and keep PRs reviewable.
- Read repository instructions and inspect relevant code/tests before editing.
- Check official 9router PRs and commits at implementation time; do not rely only on old PR descriptions.
- Keep upstream adaptations narrow and documented.
- Add regression tests for every behavior fix.
- Do not commit secrets or expose credentials in errors, logs, panel state, or diagnostics.
- Bind the local gateway to loopback by default unless the user explicitly configures and protects broader exposure.
- Use bounded retries, timeouts, concurrency, and buffering.
- Treat upstream responses and model catalogs as untrusted input.
- Keep user prompts and model output out of telemetry by default.
- Do not mark a checklist item complete until the implementation is present and validation evidence exists.

## 8. Definition of Done

A change is complete only when:
- [ ] It solves a defined user problem and fits BlackRouter's architecture.
- [ ] Tests cover normal behavior and important failure modes.
- [ ] Type-check/build and relevant CI checks pass.
- [ ] Generated bundles are reproducible from source.
- [ ] Existing API compatibility and configured egress behavior remain intact.
- [ ] Errors are actionable and secrets are redacted.
- [ ] Documentation reflects verified behavior.
- [ ] Upstream provenance and license requirements are satisfied where relevant.

## 9. Explicit Non-Goals

- Porting all of official 9router into BlackRouter.
- Porting the entire 9router-go application or its dashboard.
- Replacing the OpenChamber panel with a standalone web application.
- Adding a large number of providers before the core/provider adapter boundary is validated.
- Porting the closed Bun-sidecar PR #5235 without new evidence that it is required.
- Claiming tests, provider availability, unlimited free usage, or token-savings percentages without verification.
